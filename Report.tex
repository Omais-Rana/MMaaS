\begin{abstract}
This report documents a multimodal mobility system designed for fragmented territories and multi-operator environments. The platform ingests GTFS feeds, normalizes them into a multi-tenant data model, and provides route discovery with direct and transfer-based itineraries. It emphasizes operational resilience (large datasets, exceptions, noisy inputs), analytics for demand observation, and actionable administration via Filament. The system aligns with carbon-reduction goals through public transit prioritization, walking integration, and data-driven service optimization for underserved, discontinuous service regions.
\end{abstract}

\section{Introduction}
Fragmented territories are regions where public transport is operated by multiple agencies with discontinuous service coverage and heterogeneous data quality. This architecture targets these conditions by:
\begin{itemize}[leftmargin=1.5em]
    \item Supporting multi-tenant operators and customer and employee role separation.
    \item Ingesting GTFS data with validation, merge semantics, and incremental updates.
    \item Performing route search that mixes direct trips, walking connections, and transfers.
    \item Rendering territory polygons and route shapes for map-based MaaS experiences.
\end{itemize}

\section{System Overview}
\subsection{GTFS Import Pipeline}
The ingestion flow is built for resilience and large feed size:
\begin{enumerate}[leftmargin=1.5em]
    \item Upload GTFS archive via Filament.
    \item Queue parsing job with extended timeouts and memory limits.
    \item Extract and parse CSV files by entity, using:
    \begin{itemize}
        \item \texttt{updateOrCreate} for merge semantics.
        \item Batch inserts for shapes.
        \item Cached trip and stop lookups for stop\_times.
    \end{itemize}
    \item Commit transaction; schedule post-processing (city enrichment).
\end{enumerate}

\section{Main Algorithms}
\subsection{GTFS Parsing and Normalization}
\textbf{Approach:}
\begin{itemize}[leftmargin=1.5em]
    \item ZIP extraction into a temp directory.
    \item CSV parsing with header normalization and data alignment.
    \item Validation of required fields, graceful skipping of invalid stops.
    \item Transactional writes for consistency.
\end{itemize}

\textbf{Optimization:}
\begin{itemize}[leftmargin=1.5em]
    \item Shape points are inserted in batches to avoid memory spikes.
    \item Trip and stop caches prevent repeated lookups during stop\_time creation.
\end{itemize}

\subsection{Stop City Enrichment (Reverse Geocoding)}
\textbf{Goal:} Populate \texttt{Stop.city} without blocking GTFS imports.
\begin{itemize}[leftmargin=1.5em]
    \item First pass: reuse existing stops with same coordinates (within 100m).
    \item Second pass: cluster remaining stops within 1 km and query Nominatim once per cluster.
    \item Caching layer: short-term in-memory and 30-day persistent cache.
\end{itemize}

\textbf{Scientific method:} Haversine distance for proximity grouping; rate limiting for API sustainability.

\subsection{Route-Finding Algorithms (Actual Implementation)}
This system does not currently run a graph-wide shortest-path algorithm (for example, Dijkstra or RAPTOR) over a full time-expanded network. Instead, it implements a deterministic, data-driven routing pipeline built directly on GTFS stop\_times and trips. The algorithm is optimized for real-time use on large datasets without heavy precomputation.

\subsubsection{1) Stop Resolution and Disambiguation}
The first step is to map user inputs to concrete stop IDs. The algorithm prioritizes spatial precision:
\begin{enumerate}[leftmargin=1.5em]
    \item If GPS coordinates are available, select stop IDs within a proximity threshold.
    \item Expand to sibling platforms sharing the same stop name within a short radius.
    \item If coordinates are absent, fallback to exact stop name match, then prefix match.
\end{enumerate}

\subsubsection{2) Service Eligibility (Calendar and Exceptions)}
Service validity is computed for the requested date using:
\begin{itemize}[leftmargin=1.5em]
    \item Base calendar rules: day-of-week inclusion within start and end dates.
    \item Exception rules: calendar\_dates type 1 adds service; type 2 removes service.
    \item Fallback: if no schedule data exists, all services are considered active.
\end{itemize}

\subsubsection{3) Direct Route Search (Exact Stops)}
The algorithm queries stop\_times twice on the same trip:
\begin{itemize}[leftmargin=1.5em]
    \item Join stop\_times as origin (st1) and destination (st2).
    \item Require st2.stop\_sequence greater than st1.stop\_sequence.
    \item Enforce active service IDs and minimum departure time.
\end{itemize}
Routes are then de-duplicated by line (route short name plus operator) to avoid repetition and keep the nearest departure for each route.

\subsubsection{4) Direct Route Search (Nearby Stops)}
To support fragmented stop access:
\begin{itemize}[leftmargin=1.5em]
    \item A preloaded stop cache supports zero-query proximity scans.
    \item Nearby origin and destination stops are merged with exact stops.
    \item Two-pass priority: exact-origin to nearby-destination first, then nearby-origin.
\end{itemize}

\subsubsection{5) Transfer Search (One Transfer)}
When direct routes are unavailable, the system performs a one-transfer search:
\begin{enumerate}[leftmargin=1.5em]
    \item Compute all candidate first legs from origin to any transfer stop.
    \item Precompute all nearby transfer stops in-memory.
    \item Run one batched query for all second legs to all destination candidates.
    \item Match first and second legs in PHP, enforcing transfer time windows.
\end{enumerate}

\subsubsection{6) Walking Integration}
Walking legs are integrated using Haversine distance and speed-based time estimates:
\[
    t_{walk} = \max\left(1, \frac{d_{km}}{v_{km/h}} \cdot 60\right)
\]
Walking legs are inserted:
\begin{itemize}[leftmargin=1.5em]
    \item From origin to the boarding stop (if not exactly at stop).
    \item Between transfer stops (if transfer requires spatial movement).
    \item From alighting stop to destination.
\end{itemize}

\subsubsection{7) Journey Scoring and Ranking}
Journeys are scored using a weighted penalty model:
\[
    score = 10000 - 50 \cdot T - 200 \cdot X - 10 \cdot W
\]
where:
\begin{itemize}[leftmargin=1.5em]
    \item $T$ = total journey time in minutes,
    \item $X$ = number of transfers,
    \item $W$ = total walking distance (km).
\end{itemize}
Journeys are deduplicated by route identity plus transfer count, then sorted by score.

\subsubsection{8) Midnight-Safe Time Arithmetic}
Trip durations and waits are computed with a midnight rollover guard:
\begin{itemize}[leftmargin=1.5em]
    \item If arrival time is earlier than departure, add 24 hours.
    \item Prevent negative durations that would distort scoring.
\end{itemize}

\subsubsection{9) Shape Clipping for Map Presentation}
Route geometry is clipped to the trip segment only:
\begin{itemize}[leftmargin=1.5em]
    \item Find nearest shape points to origin and destination stops.
    \item Slice the shape polyline between those indices.
\end{itemize}
This provides accurate map segments while reusing GTFS shapes.

\subsubsection{10) Caching and Performance Strategy}
\begin{itemize}[leftmargin=1.5em]
    \item Stop cache: preloaded once per request, reused for all distance checks.
    \item Shape cache: per-request in-memory caching of shape points by shape\_id.
    \item Route shapes cache: persistent cache for map visualization.
\end{itemize}

\subsubsection{Position Relative to Dijkstra and RAPTOR}
The current pipeline resembles a constrained, GTFS-join-based search rather than a full graph shortest-path. It is optimized for:
\begin{itemize}[leftmargin=1.5em]
    \item Quick response for fragmented datasets.
    \item Minimal precomputation.
    \item Controlled scope (direct plus one-transfer).
\end{itemize}
If a future roadmap includes full multimodal graph routing (Dijkstra, RAPTOR, or CSA), the existing stop cache, transfer handling, and exception-aware calendar logic provide a strong foundation.

\subsection{Territory Polygon Generation}
\textbf{Objective:} Represent each operator's spatial service footprint for MaaS browsing.
\begin{itemize}[leftmargin=1.5em]
    \item Collect stop points and representative shape points.
    \item Build a concave shell-like polygon using:
    \begin{itemize}
        \item Convex hull baseline.
        \item Centroid expansion.
        \item Simplification and Chaikin smoothing.
        \item Bounding box fallback if required.
    \end{itemize}
    \item Compute bounding boxes for map framing.
\end{itemize}
